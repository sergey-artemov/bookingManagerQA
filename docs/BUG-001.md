# BUG-001: Двойное бронирование одного номера на пересекающиеся даты

| Поле | Значение |
|------|----------|
| ID | BUG-001 |
| Приоритет | High |
| Серьёзность | Критическая (нарушение бизнес-логики) |
| Статус | Open |
| Требование | Правило R8 (см. README «Бизнес-правила») |

## Окружение

- Приложение: Booking Manager QA (Spring Boot 3.5.7), `http://localhost:8080`
- БД: PostgreSQL 15 (Docker), база `bookingsdb`
- Инструмент: Talend API Tester

## Предусловия

Сервис запущен (`mvn spring-boot:run`). Номер 305 свободен.

## Шаги воспроизведения

1. `POST /api/bookings/new`

   ```json
   {"roomNumber": 305, "bookedFrom": "2026-12-01", "bookedTo": "2026-12-05", "guestName": "Иванов Иван Иванович"}
   ```
   → ответ 201 Created.
2. `POST /api/bookings/new`

   ```json
   {"roomNumber": 305, "bookedFrom": "2026-12-03", "bookedTo": "2026-12-06", "guestName": "Петров Пётр Петрович"}
   ```
   → ответ **201 Created**.

## Фактический результат

Обе брони успешно созданы. Один и тот же номер (305) забронирован двумя разными гостями на пересекающиеся даты (01–05.12 и 03–06.12). Проверка в БД:

```sql
SELECT * FROM bookings WHERE room_number = 305;
-- 2 строки с пересекающимися периодами
```

## Ожидаемый результат

Второй запрос возвращает **409 Conflict** с сообщением вида «Номер 305 уже забронирован на выбранные даты». В БД — одна бронь на пересекающийся период.

## Комментарии

- Аналогичный дефект воспроизводится через `PUT` (см. чек-лист, PUT-04): изменение существующей брони может создать пересечение.
- Связанные проверки, которые нужно сохранить после фикса: стыковые даты (выезд 05.12 / заезд 05.12) — должно разрешаться; соседние этажи — не блокируются; один и тот же гость на непересекающиеся даты — разрешается.
- Регресс после фикса: интеграционный автотест (Rest Assured + Testcontainers) «двойное бронирование → 409».
